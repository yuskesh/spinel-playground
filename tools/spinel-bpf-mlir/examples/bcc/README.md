# examples/bcc — Ruby versions of bcc tools (written the spinel-bpf-mlir way)

The bcc tools in `tools/` of spinel-ebpf (commit 23fa4b0), ported to the way spinel-bpf-mlir writes programs (P027 — origin in [PROVENANCE.md](PROVENANCE.md)).
Each tool is 1 Ruby program (eBPF side and user-space side) plus its committed artefacts. `spinelbpf build -o <tool> examples/bcc/<tool>/<tool>.rb` makes it 1 executable; run it as root.

- `--selftest` — triggers its own events and checks the kernel's results (tools that attach system-wide filter by their own pid / tid / port)
- default — measures for `--duration-ms MS` and prints a table or a histogram (some tools can filter with `--pid`)

**Reproduction condition for sslsniff** (E158): the artefacts carry the SHA-256 of the build host's libssl — **`/usr/lib/x86_64-linux-gnu/libssl.so.3` of libssl3t64 3.5.7-1~deb13u3 (sha256 `9592038e92d1f41affcbb625334d0b6e788714c889104fa6d5b107cf9fd657f2`)** — and the check reads `/usr/lib/debug/.build-id/4f/18cdec63410d6a18616448c922fb580ca2c292.debug` of libssl3t64-dbgsym (trixie-security-debug of deb.debian.org/debian-security-debug — the user's approval 2026-10-27). A libssl update changes the artefacts and their artefacts.sha256 lines (`TestBccLibsslCondition` names it)

**Reproduction condition for gethostlatency and deadlock** (the bpf-mlir coordinator i1168): the artefacts (the schema's `binary_sha256` and the ELF requirements) carry the SHA-256 of the build host's libc — **`/lib/x86_64-linux-gnu/libc.so.6` of libc6 2.41-12+deb13u4 (sha256 `9792e3cbb541c8f44c7acf5f14f4022ea62998ecc787d326bed4d8b6547dfd92`)** — and the build-time and load-time checks read `/usr/lib/debug/.build-id/5e/5b51f4c39af9ac589408c1dc432ba390a273cc.debug` of libc6-dbg. When libc is updated, the artefacts and their artefacts.sha256 lines change (`TestBccLibcCondition` names the libc difference — deadlock has the same libc sha256), and load stops an executable with old artefacts with TargetRejected (`binary`) — rebuild it

**Privileges** (requested by spinel-extended — not re-measured, known facts only): every selftest was run as root (sudo). **root (TP)** = the tracepoint kind — the pre-load check of the tracefs format stops the load with `tpfield_unknown` when tracefs cannot be read (E114 — non-root load is not tested, capability sets are not measured). **root (KP)** = kprobe / kretprobe — non-root is not measured. Measured non-root capabilities (the release notes v0.1.0 section): tp_btf needs CAP_BPF + CAP_PERFMON (E087), uprobe needs CAP_BPF + CAP_PERFMON + CAP_SYS_ADMIN (E081 / E083); non-root fentry, fexit, kprobe, kretprobe, raw_tp and ksyscall are not measured

## Tools moved to wave 2, wave 3 or to the user's decision (reasons and required capabilities — the source of the P027 E140 list)

A **wave** is a porting batch: wave 1 is P027, wave 2 is P028 and wave 3 is P029. In the wave column, `2-done` / `3-done` mean the tool was ported in wave 2 / wave 3 (it was first deferred there).
"After the first release" refers to the user's decision (2026-10-25) to port a tool only after the first release.
